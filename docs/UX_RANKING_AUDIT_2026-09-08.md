# TYPE BURST UX・ランキング監査（2026-09-08）

## 結論と範囲

ランキングAPI全体が停止している状態ではない。ただし「全ユーザーに常に最新で、整合したランキングを見せる」と保証できる実装にはなっていない。デイリーの保存処理、表示の更新契機、難易度の引き継ぎを先に修正するべき。

本番ホーム・世界ランキングを操作し、本番のランキングAPIをGETで確認した。ローカルではチュートリアルの入力→Enterで次へ、神級サバイバルの入力→終了→結果→タイピング分析を操作した。ソースではデイリー、モバイルプレビュー、保存・送信・キャッシュ処理も確認した。

本番にテストスコアは送信していない。Redis内部の全件照合、複数端末による本番の同時送信、全画面幅の実機確認は未実施。ソースから特定したリスクと実画面で再現した事象を区別する。以下の実装状況は、この監査後の修正を追記したもの。

## 監査後の実装状況（2026-09-08）

R1/R2/R6/R7 はデイリー開始枠をサーバーで予約する一回限りのチケット方式へ変更し、Redis Luaで回数消費・最高スコア・詳細・重複送信を原子的に処理した。日付境界には開始時刻を基準にした短い終了猶予を設け、チケットなしのランキング送信は受理しない。

R3/R4/R5/R8 は、世界・デイリー・ホーム・モバイルの取得を明示的に再取得できる状態へ揃え、フォーカス/タブ復帰と30秒更新、難易度の引き継ぎ、上位100件と登録記録数の表示、順位を詰めない欠落行の扱い、原子的な圏外整理を追加した。

R9 は結果画面の再送に加え、通信失敗時に難易度ごとの最高記録だけを端末内へ保留し、次回のタイトル表示・復帰・30秒間隔で静かに再送する outbox を追加した。入力本文・分析データ・playerIdは保留しない。

U1〜U4/U7 は、ゲームHUDの最大高さ予約とプレイ中の内容ResizeObserver停止、低い画面向けの補助余白調整、分析の入口別並び替え、成長グラフの現行ルール/難易度フィルタ、少量データ向けの表現修正で対応した。U5 は初回に難易度/FOCUSを隠してチュートリアルを主導線にし、U6 は未配信広告枠を自動で空けるCSSを追加した。ランキング/デイリー/モバイルの取得中・失敗状態には再試行とARIA状態を付けた。

実装後のローカル検証は `npm run typecheck`、`npm test -- --run --reporter=dot`（37ファイル・274テスト）、`npm run build`（35 URLのサイトマップ生成、118モジュールのViteビルド）を通過している。本番の既存データを削除・書き換える操作は行っていない。

## 優先1：ランキングの正確性・更新

### R1 デイリーの最高得点と詳細が別プレイになる（コードで特定）

- 根拠：`apps/web/api/daily-scores.ts:110` 以降。
- スコアはpreviousScoreとの最大値を保持する一方、KPM・正確率・最大連鎖・時間・送信日時は毎回新しい送信値で上書きする。
- 例：10万点の後に5万点を送ると「10万点＋5万点の回の正確率」になる。
- 修正：最高記録を更新したときだけ、そのプレイの詳細を一体で更新。同点の扱いも明文化する。
- 受入：低得点・同点の再送で最高記録の詳細が変わらない。表示名の変更は別の明確な規則にする。

### R2 デイリーの同時送信で最高得点が下がり得る（コードで特定、実損未確認）

- 同じ処理は読取→最大値計算→pipeline書込であり、比較と更新が不可分ではない。
- 例：2リクエストが旧100点を読み、300点の書込後に200点側が書くと200点に戻り得る。
- 修正：サバイバル側で既に使っているようなRedis Luaによる比較・スコア・詳細の原子的更新。
- 受入：送信順・到着順を逆転しても最高点とその詳細を保持。重複再送でも増殖しない。

### R3 表示を開いたままでは最新順位にならない（コードで特定）

- `RankingScreen.tsx` の取得は難易度変更・エラー再試行時。成功後の手動更新、タブ復帰時更新、定期更新はない。
- `HomeDecks.tsx` のプレビュー、モバイル・デイリーのプレビューにも同種の更新不足がある。
- 公開APIには `s-maxage=30, stale-while-revalidate=60`、viewer付きAPIにはprivate/no-storeという差もある。
- 重要：画面自体が再取得しない限り、古い表示は90秒を超えて残る。キャッシュ時間だけ短くしても解決しない。
- 修正：画面表示時・タブ復帰時・送信成功後の再取得、明示的な更新ボタン、最終取得時刻。連打・多重取得を抑制する。
- 受入：別クライアントでの更新を復帰/更新操作で反映し、ホームと詳細を同条件で比較できる。

### R4 上級のプレビューから中級ランキングが開く（本番実画面で再現）

- ホームで上級を選択→上級プレビューを押す→詳細は中級が選択される。
- 根拠：`RankingScreen.tsx:47` の初期値normal、`App.tsx`から難易度を渡していない。
- データが消えたわけではないが、先ほどの順位と違う・反映されていないと思わせる。
- 修正：入口の難易度を渡し、戻る場合も選択を維持する。

### R5 「人数」「全順位」と実際の集計対象が一致していない（コードで特定）

- プレイヤーは会員アカウントではなくブラウザ保存の匿名ID。同じ人でも別端末・別ブラウザ・保存消去で別IDになる。引き継ぎを使えば継続可能。
- 旧方式の記録は同じ人のものか安全に判定できず、旧エントリとして残る。ニックネームの一致だけでは同一人物と判断できない。
- `全○人中` の母数はランキング登録エントリ数。実人数とは限らない。
- `全順位を見る` の詳細リストは最大100件で、サーバの保持上限は500件。
- 修正：集計単位・上位100件・自己順位を明示。旧記録は無断削除/名前による統合をせず、履歴との区別を設計する。

### R6 デイリーの1日3回をサーバが保証していない（コードで特定）

- 回数はローカル進捗で管理され、daily-scores APIでは回数制限を検証していない。
- スコアもクライアント申告値の上限チェックであり、プレイ完了や点数計算のサーバ検証ではない。
- 不正が実際に発生したと断定する根拠はない。ただし公平性を保証するには不足する。
- 修正：匿名IDのまま、サーバ側の挑戦枠予約、プレイ識別子、重複送信防止、レート制限・段階的な妥当性検証を設計する。単なる人数増加目的の会員登録必須化は不要。

### R7 日付をまたぐデイリーが拒否される可能性（コードで特定）

- サーバは送信時点のJST当日とchallengeIdが一致する場合だけ受理する。
- 23:59開始→翌日終了は旧日付になるため拒否される。開いたままの日付更新にも専用の更新契機がない。
- 修正：開始時の日付確認、日付変更時の表示更新、正規の開始記録に基づく短い終了猶予を定義する。
- 受入：23:59開始、日付変更後の再送、日付変更をまたいだホームの放置をテストする。

### R8 500件超の整理と新記録更新が競合する（将来リスク）

- `apps/web/api/scores.ts:337` 以降で圏外候補取得と削除が分離している。
- 削除候補に選ばれた直後に高得点へ更新されたプレイヤーを削除してしまう可能性がある。
- 現在確認した件数ではこの事象を観測していない。
- 修正：削除時点の順位再確認を原子的に行う。公開ランキングの上限と、個人最高記録の永続保持は分けて考える。

### R9 送信失敗後に結果画面を離れた場合の回復導線が弱い（コードで特定）

- 結果画面内の再送ボタンは既にある。一方、未送信記録を後からまとめて再送する導線はない。
- fetchに明示的なタイムアウトがなく、通信状況によって送信中・読込中が長引く。
- 修正：明示的なタイムアウト、エラー種別の適切な表示、未送信最高記録の回復手段。サーバ側の冪等性とセットで検討する。

## 優先2：ホーム・ゲーム・結果・分析の体験

### U1 ゲーム画面の小さい文字とHUDの空白（実画面＋コード）

神級の長文とHUDの補助説明は、低いビューポートに全体を縮小すると読み取りにくい。現在は伸縮を防ぐためHUDの可変要素の領域を予約しており、その空白も全体の高さを押し上げる。

修正案：固定した盤面寸法を維持しつつ、TIME/SCORE・現在入力・BURSTを優先。非発動時のFEVERや補足説明は小さな一定高の表示に集約する。プレイ中に動的に全体を再縮小する方式に戻さない。文字サイズ設定と併せ1280×720、1440×900、1920×1080を実機検証する。

### U2 今回の分析より累計・週間集計が先に表示される（実画面で確認）

結果の「タイピング分析を見る」から遷移しても、初期表示は称号・自己ベスト・累計・週間集計。今回のキー別分析や前半/後半のペースまでスクロールが必要。

修正案：結果から来たら「今回の分析」を最上部、ホームの成長記録から来たら「成長」を最上部にする。同じページでも入口に合った初期タブを選ぶ。

### U3 プレイ済みなのに成長グラフが空に見える（本番実画面＋コード）

ホームで23戦・ベストKPM等がある一方、グラフは記録が増えるまで描画されない表示だった。累計は全期間、グラフ入力は現行survival-v2の記録だけという対象差がある。

修正案：「累計23戦／現行ルールの比較対象○戦」等の説明。旧記録を消さず履歴として閲覧可能にする。比較データ0件と1件で案内を分ける。

### U4 成長グラフが異なる難易度のスコアを混ぜる（コードで特定）

週間比較は同一難易度を選んでいるが、ホームのスパークラインとホーム経由の成長推移には難易度をそろえるフィルターがない。難易度を変えただけのスコア差を上達/悪化と解釈させる。

修正案：難易度を選べるグラフ、比較条件のラベル、データが不足する場合の明確な表示。KPMも問題の長さの影響を説明する。

### U5 初回から目標・特殊用語の選択が多い（設計改善案）

主な開始ボタンに加え、難易度、FOCUS（PERFECT/CHAIN/POWER/MAX BURST）、CPU、ランキング、デイリーが並ぶ。初回は言葉の意味を知らない段階で選択を求める。

修正案：初回は開始と基本説明を主役にし、FOCUSは1回プレイ後に段階的に案内する。再訪者のランキングやデイリーは隠さない。「次に何をすればいいか」をユーザー段階別に絞る。

### U6 未配信の広告枠が白い大きな矩形に見える（本番観測）

ホーム左右で白い縦長領域が目立つ場面があった。広告の審査状態・配信障害をこの観測だけで断定するものではない。

修正案：未配信/読込待ち時の外側レイアウトを点検し、余分な空枠を目立たせない。広告本体への重ね描きやクリック誘導は行わない。左右の中央本文への整列は現在のCSSで既に改善済み。

### U7 少ない打鍵でも「正確率が安定」と断定する（ローカルで再現）

1文章・31打鍵・100%の結果に対して、次の目標の理由が「正確率が安定しているので」と表示された。今回100%という事実と、複数回で安定していることは別。

修正案：少量データでは「今回はミスなしでした」。複数回・一定打鍵数がそろってから安定判定を使う。結果の称号表示も新規獲得と現在の称号を区別すると報酬の信頼感が増す。

## 良好だった点・再発扱いにしない点

- 本番世界ランキングは4難易度とも取得でき、確認範囲でスコア降順だった。
- サバイバルの最高点と詳細の更新はLuaで一体化されている。今回のデイリーの不具合と混同しない。
- ランキングのレスポンスに匿名playerIdは含まれていなかった。
- チュートリアルで単語入力後に次へへフォーカスし、Enterで進むことを確認した。
- ローカルの入力にpを含む文章を完了できた。Pで一時停止する過去のバグは今回再現していない。
- 結果画面は確認したデスクトップ画面でブランド・スコア・ランク・スタッツ・4つの操作が収まっていた。大きな重なりはなかった。
- 分析画面の横幅は活用されており、昔の極端に細い1列表示とは異なる。
- 世界/デイリーの取得失敗時や保存済みニックネームでの送信失敗時には再試行導線が既に存在する。
