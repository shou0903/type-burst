# ローマ字入力ラボ：SEO・プロダクト方針

最終更新: 2026-08-01
状態: **採用（ただし、添付案をそのままではなく下記の範囲に改めて段階実装する）**

## 1. 結論

「ローマ字入力ラボ」は、次に取り組むべきSEO施策として採用する。既存の解説記事をさらに量産するより、検索者がその場で問題を解決し、実際に打鍵できる**固有のツール**を作る方が、TYPE BURSTにしかない価値とゲームへの自然な導線を両立できるためである。

ただし、単なる「日本語→ローマ字変換サイト」にはしない。TYPE BURSTのローマ字入力ルールを正確に確認・試打できるツールとして位置付ける。これにより、既存のローマ字表・解説記事と競合せず、誤った候補を表示するリスクも避ける。

公開URLは、既存サイトのURL正規化（末尾スラッシュなし）に合わせ、`https://type-burst.com/romaji` を正規URLとする。添付案の `/romaji/` を正規URLにはしない。

## 2. なぜ今これを優先するか

現在は、ローマ字入力の基本解説、`ん`、小さい文字、早見表などの静的コンテンツがすでに存在する。次に必要なのは、検索流入した人が「自分がいま困っている文字」をすぐ解決できる体験である。

ローマ字入力には `ん`、促音の `っ`、小書き文字、外来語など、表だけでは不安が残る場面がある。TYPE BURSTには、それらの複数入力候補を実ゲームで判定するローマ字エンジンがすでにある。正しい入力を説明するだけでなく、同じ判定でその場で打鍵確認できることが、一般的な早見表との差別化になる。

検索面では、以下の意図を一つのページで自然に満たせる。

- 「ローマ字 打ち方」「ローマ字 入力 練習」: 調べて、その場で打つ
- 「ん ローマ字」「小さいっ ローマ字」: ルールを確認して、候補を試す
- 「ティ ローマ字」「トゥ ローマ字」「ヴ ローマ字」: 外来語の入力候補を確認する

一方で、「漢字を含む文章を何でもローマ字に変換したい」という一般的な変換需要は、現行ゲームエンジンの責務ではない。ここを曖昧にして広い「日本語ローマ字変換」検索を狙うと、利用者の期待とツールの実態がずれる。初期版では**かな入力のローマ字打ち方・練習**に集中する。

## 3. 既存ページとの役割分担

| ページ | 担当すること | ラボとの違い |
| --- | --- | --- |
| `/tools/romaji-table.html` | よく使う文字の一覧を素早く参照する | 一覧から探すページ。任意のかな列の判定や試打は行わない。 |
| `/guides/romaji-n-input.html` | `ん` のルール・理由を理解する | ラボでは自分の文字列を確認・試打する。 |
| `/guides/romaji-small-kana.html` | `っ`・拗音・小書き文字のルールを理解する | ラボでは実際の入力候補を検証する。 |
| `/guides/romaji-typing-practice.html` | 継続練習の方法を学ぶ | ラボでは短い確認・ドリルからゲームへ進む。 |
| `/romaji` | 任意のかな列を調べ、TYPE BURSTと同じ判定で試す | 解説の複製ではなく、インタラクティブな解決手段。 |

各既存ページからラボへは、「この文字を実際に試す」のように文脈が自然な箇所だけをリンクする。ラボ側からは、入力内容の種類に応じて既存ガイドへ補足リンクを出す。機械的な相互リンクや、同じ本文の再掲はしない。

## 4. 初期版で実装する範囲

### 4.1 調べる

- 入力欄は **ひらがな・カタカナ・長音記号（ー）** を受け付ける。漢字や記号を含む文章は、かなで入力するよう明確に案内する。
- 入力は正規化して、TYPE BURST本編と同じローマ字エンジンで解析する。
- 表示するのは以下に限定する。
  - 推奨入力: 本編で標準として案内する候補
  - 最短入力: 推奨入力と異なる場合のみ
  - ほかに使える主な候補: 上限付き（最大8件）
- 「すべてのローマ字候補」を保証・表示しない。候補数が多い場合は、表示を省略した旨を伝える。
- 文字数にも上限を設ける（初期案: 40文字）。これは候補の組み合わせ爆発と、意図しない長文変換用途を防ぐためである。

### 4.2 試す

- 結果の直下で、表示されたかな列をすぐに入力できる試打エリアを提供する。
- 成功した文字、次に受け付けるキー、完了状態をキーボード操作だけでも分かるようにする。
- 判定は必ず `TypingAutomaton` を用いる。別のローマ字変換ライブラリや、ラボ専用の独自判定は使わない。

### 4.3 20秒ミニドリル

- 初期版に、`ん`、促音、小書き文字、外来語、混合の5種類程度の短い静的ドリルを含める。
- 問題文はあらかじめ選定したかな列だけを使い、ユーザーが入力した文字列をサーバーに保存したり、問題として再配信したりしない。
- ドリル完了後は、同じ課題をゲームで練習できるCTAを表示する。ただし、ゲームの難易度やモードを誤認させる表現はしない。

### 4.4 検索ページとして必要な静的要素

- 固有の title / meta description / canonical / OGP
- 画面に実際に表示される、短く実質的な説明とFAQ
- `WebApplication` と `BreadcrumbList` のJSON-LD
- 無料・登録不要・PCブラウザで使えること、IMEをオフにして打つことの明記
- ツール一覧・ローマ字表・関連ガイド・ゲーム本体への自然な内部リンク

FAQはリッチリザルトだけを目的に増やさず、「かな以外は使えるか」「`ん` や `っ` の候補はなぜ複数あるか」「ゲームと判定は同じか」といった、画面上で実際に生じる疑問だけに絞る。

## 5. 先に行う技術検証（実装の着手条件）

既存の `TypingAutomaton` は受理判定・進捗表示には使えるが、受理可能な入力列を公開用に列挙するAPIは持っていない。ここは画面側で場当たり的に再実装してはいけない。

ラボ実装の最初の作業は、typing-engine に以下のような**上限付きの候補列挙機能**を追加する技術検証とする。

1. かなを既存の `segmentKana()` で分割する。
2. 優先順を保った深さ優先探索で候補を生成し、上限に達したら探索を打ち切る。
3. 生成した各候補を `TypingAutomaton` で最後まで入力して受理されたものだけを採用する。
4. `truncated`（候補が多いため省略したか）を返す。
5. `ん`、促音、拗音、小書き母音、外来語、カタカナ入力、長音記号、上限超過・未対応文字を含む回帰テストを追加する。

候補の「推奨」は常に決定的でなければならない。短いことだけを優先するのではなく、本編が通常表示する入力を第一候補にする。最短候補を併記する場合も、ゲーム本編で実際に受理されることを検証する。

## 6. SEOの実装方針

### 採用すること

- 正規URLは `/romaji`。`/romaji/index.html` は恒久リダイレクトする。
- JavaScriptが無効でも、ページの目的・対応範囲・FAQ・関連リンクは読めるHTMLに置く。
- ラボをViteの独立エントリーにし、ゲーム画面一式を読ませない。初回表示のJavaScriptを小さく保つ。
- sitemap、静的SEO監査、内部リンク監査の対象へ明示的に追加する。
- 分析イベントは、入力本文を送らない匿名の分類データだけにする。例: `n` / `sokuon` / `small-kana` / `foreign-sound` / `other`、試打開始、ドリル完了、ゲームCTAクリック。
- 上記イベントを入れる際は、プライバシーポリシーに「入力内容そのものは収集しない」ことを追記する。

### 採用しないこと

- 検索語ごと・入力語ごとに数百〜数千ページを自動生成すること
- `thi`、`dhi`、`tu` などの小ページを最初から量産すること
- 漢字を含む文章の汎用ローマ字変換をうたうこと
- ユーザーの自由入力を保存、送信、学習データ化すること
- ラボ専用の入力ルールを作り、ゲーム本編と判定がずれること

## 7. 段階的な公開判断

### Phase 0: エンジン検証

候補列挙の仕様と回帰テストを完成させる。ここで誤判定・候補爆発・入力ルールのずれが見つかった場合は、UI公開を急がずエンジン側を直す。

### Phase 1: ラボ公開

`/romaji` に調べる、試す、20秒ミニドリル、静的SEO要素、関連リンクをまとめて公開する。公開前に typecheck、テスト、ビルド、静的SEO監査、キーボードのみの手動確認を通す。

### Phase 2: 実データで改善

公開後、少なくとも28日間、またはラボの十分な操作データが集まった時点で以下を確認する。

- Search Console: 表示された検索語、掲載順位、CTR、ランディングページ
- 分析: 調べる → 試す → ドリル完了 → ゲーム開始の遷移率
- エラー: 未対応入力、候補省略、IMEの誤操作による離脱

CTRが低い場合は title / description と冒頭の約束を修正する。試打率が低い場合は入力例・結果表示を改善する。ドリル完了後のゲーム遷移が低い場合は、課題とゲームCTAの結び付きを見直す。

### Phase 3: 子ページは証拠が出てから

個別ページを追加するのは、Search Consoleで明確な需要が確認でき、既存の早見表やガイドでは答え切れない固有の実用価値を作れる場合だけにする。最初の候補は `ティ`、`ディ`、`トゥ`、`ヴ` などだが、検索データなしにページ数を増やす決定はしない。

各子ページを作る場合も、重複した説明文ではなく、具体例、入力候補、試打への初期状態、よくある誤り、関連ルールを持たせる。子ページは一度に最大3本までとし、評価後に次を判断する。

## 8. 成功指標

SEOの成否をインデックス数だけで判断しない。ラボでは、検索流入がゲーム利用へつながることを最終指標にする。

| 層 | 観測すること | 判断 |
| --- | --- | --- |
| 検索 | 表示回数、CTR、平均掲載順位、流入検索語 | どの課題に実需要があるかを知る。 |
| ツール利用 | 調べる・試す・ドリル完了率 | ページが検索意図を解決できているかを知る。 |
| 送客 | ラボ経由のゲーム開始率 | TYPE BURSTの新規利用者獲得に寄与しているかを知る。 |
| 品質 | 未対応入力率、候補省略率、エラー率 | 期待と対応範囲のずれを見つける。 |

検索流入月間5,000人という全体目標に対し、ラボだけで達成を約束しない。ラボは「ローマ字入力」クラスターの中核にし、既存ガイド改善、速度測定ツール、今後の検索データに基づくテーマ追加と合わせて伸ばす。

## 9. 実装時のチェックリスト

- [ ] `/romaji` と `https://type-burst.com/romaji` のcanonical / OGP / sitemapを一致させる
- [ ] ラボ用に本編と別のローマ字規則を作らない
- [ ] 候補の上限・省略・未対応文字をUIで明示する
- [ ] 入力本文を分析・ログ・APIに送らない
- [ ] `prefers-reduced-motion` とキーボード操作を尊重する
- [ ] title、description、本文、FAQの検索意図を一致させる
- [ ] 既存の早見表・`ん`・小書き文字ガイドと本文重複を起こさない
- [ ] typecheck / test / build / `seo:audit` を通す
- [ ] 公開後にSearch ConsoleでURL検査と実データ確認を行う

## 10. 今後のSEO全体における優先順位

1. ローマ字入力ラボのPhase 0〜1を品質優先で完成させる。
2. Search Consoleの実クエリと既存記事のCTRを確認し、既存ページの改善を先に行う。
3. ラボの実利用データを根拠に、必要な個別ページを少数追加する。
4. 十分な匿名集計データがたまった後にのみ、実測に基づくタイピング学習コンテンツを検討する。

この順序なら、量産型SEOではなく、「検索者の課題を解決できる道具」と「TYPE BURSTでしか得られない体験」を積み上げられる。
